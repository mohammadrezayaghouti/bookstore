# BookStore

A desktop BookStore client built with **C++ / Qt 6 (Qt Widgets)**, backed by a **Django REST Framework** API. Users can register, browse and search a shared book catalog, list their own books for sale, manage a shopping cart, purchase items, and view their purchase history — all through a single native desktop application talking to the backend over HTTP/JSON.

This is a university course project. The backend is a local development server (SQLite, `DEBUG=True`) and is not configured for production deployment.

## Overview

BookStore is split into two independent parts:

- **Frontend** — a Qt Widgets desktop application (this repository) that renders the UI and talks to the backend exclusively through `QNetworkAccessManager`.
- **Backend** — a Django + Django REST Framework API (separate project directory) that owns all data: users, books, and cart items, persisted in SQLite.

The two communicate over plain HTTP with JSON request/response bodies, authenticated with JWT access/refresh tokens.

## Features

Implemented and verified in the source:

- User registration (`POST /api/users/`)
- JWT login (`POST /api/token/`) with the access token attached to all subsequent authenticated requests
- Browse the shared book catalog on the Home page, with book cover images
- View book details in a dedicated dialog
- Add a new book for sale, including a cover image upload (multipart form)
- **My Books** — books the current user has listed for sale
- Shopping Cart: add to cart, change item quantity (+/-), remove an item
- Purchase the current cart
- **My Purchases** — books the current user has successfully purchased, loaded from the backend
- User Profile: view/update profile fields, logout
- A single, centralized light-theme stylesheet (`styles.qss`) applied application-wide
- Swagger (`/swagger/`) and ReDoc (`/redoc/`) API documentation, auto-generated by `drf-yasg`

## Known Limitations

- The Home page search box is present in the UI but does not currently filter the book grid — it's wired up but not yet implemented.
- Purchase history has no date/timestamp: the `CartItem` model has no order date field, so **My Purchases** shows *which* books were bought but not *when*, and can't show quantity or price actually paid per purchase (the endpoint it uses returns plain book data, not cart-item data).
- No automated test suite — `api/tests.py` is the default Django stub with no tests implemented.
- No `requirements.txt` is currently checked into the backend project; see [Running the Backend](#running-the-backend) for the packages that need to be installed manually.
- The backend runs with development-only settings (`DEBUG=True`, `ALLOWED_HOSTS=['*']`, a hardcoded `SECRET_KEY`) and is meant for local development, not production use.
- Only a light theme is implemented; there is no dark mode.

## Tech Stack

**Frontend**
- C++17
- Qt 6 (Qt Widgets, Qt Network)
- CMake (Ninja/MSVC/MinGW toolchains)
- `QNetworkAccessManager` / `QNetworkRequest` / `QNetworkReply` for HTTP

**Backend**
- Python / Django 5.1
- Django REST Framework
- `djangorestframework-simplejwt` (JWT authentication)
- `drf-yasg` (Swagger / ReDoc API documentation)
- SQLite (default Django database)
- Pillow (required by Django's `ImageField`, used for book cover uploads)

## Architecture

```
Qt Desktop Client (C++ / Qt Widgets)
        |
        | HTTP / JSON  (QNetworkAccessManager)
        v
Django REST Framework API
        |
        v
SQLite (db.sqlite3)
```

- The Qt client owns all UI and navigation; it never talks to the database directly.
- All backend communication goes through a single `NetworkManager` singleton (`networkmanager.h/.cpp`), which attaches the `Authorization: Bearer <access_token>` header to every authenticated request and converts responses into a small `ApiResponse` struct (success flag, HTTP status, parsed JSON, error message).
- Authentication is JWT-based: the client logs in against `/api/token/`, stores the returned access token in `NetworkManager`, and reuses it for every subsequent request for the lifetime of the session.
- Django REST Framework exposes the API as a set of `ViewSet`s (users, books, cart) plus a couple of dedicated views, documented automatically via `drf-yasg`.
- SQLite is the only data store; uploaded book cover images are saved under `media/book_covers/` and served back by Django's media handling in development.

## API

Base URL: `http://127.0.0.1:8000/api/`

All endpoints below are registered in `api/urls.py` (via a DRF `DefaultRouter`) and `BookStore/urls.py`, and were verified against the actual view implementations.

**Authentication**
```
POST /api/token/            # obtain access + refresh JWT tokens
POST /api/token/refresh/    # refresh an access token
```

**Users**
```
POST   /api/users/          # register a new account (open to anyone)
GET    /api/users/{id}/     # requires authentication
PUT    /api/users/{id}/
PATCH  /api/users/{id}/
GET    /api/user-detail/    # current authenticated user's profile
```

**Books**
```
GET    /api/books/          # list the shared catalog (read is open; writes require auth)
POST   /api/books/          # add a book (multipart form, sets owner from the JWT)
GET    /api/books/{id}/
PUT    /api/books/{id}/
PATCH  /api/books/{id}/
DELETE /api/books/{id}/
GET    /api/books/my_books/ # books the current user has listed for sale
```

**Cart**
```
GET    /api/cart/                 # raw CartItem list (not used directly by the client)
GET    /api/cart/my_cart/         # current user's unpurchased items: {"items": [...], "total": ...}
POST   /api/cart/add_to_cart/     # body: {"book_id": <id>, "quantity": <n>} — increments quantity on repeat
PATCH  /api/cart/{cart_item_id}/  # body: {"quantity": <n>}
DELETE /api/cart/{cart_item_id}/  # remove a cart item
POST   /api/cart/purchase/        # marks all of the user's unpurchased items as purchased
GET    /api/cart/my_books/        # books the current user has purchased (plain Book objects)
```

Note the two similarly-named endpoints: `/api/books/my_books/` returns books the user **added** as a seller, while `/api/cart/my_books/` returns books the user has **purchased**. They are backed by different viewsets and are not interchangeable.

**Documentation**
```
GET /swagger/   # interactive Swagger UI
GET /redoc/     # ReDoc UI
```

## Authentication

1. The user submits a username and password from the Login screen.
2. The client `POST`s them to `/api/token/`. On success, the backend (via `rest_framework_simplejwt`) returns an `access` and a `refresh` JWT.
3. The Qt client stores the access token in the `NetworkManager` singleton and attaches it as `Authorization: Bearer <access_token>` on every authenticated request from then on.
4. Server-side, `rest_framework_simplejwt.authentication.JWTAuthentication` is the default authentication class, and `IsAuthenticated` is the default permission — endpoints that should be public (registration, catalog browsing) explicitly override that.

No real usernames, passwords, or tokens are included anywhere in this repository or this document.

## Running the Backend

The backend project does not currently include a `requirements.txt`. Based on `BookStore/settings.py` (`INSTALLED_APPS`) and the models/views, the following packages are required:

```bash
cd server/BookStore-V_2-0-0/BookStore
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS/Linux
source .venv/bin/activate

pip install django djangorestframework djangorestframework-simplejwt drf-yasg pillow

python manage.py migrate
python manage.py runserver
```

The API will then be available at `http://127.0.0.1:8000/api/`, with Swagger UI at `http://127.0.0.1:8000/swagger/`. The repository already includes a `db.sqlite3` with existing data, so `migrate` should only need to apply any pending migrations.

## Running the Frontend

Requirements: Qt 6 (Widgets + Network modules) and CMake. The project was built and tested with Qt 6.10 on Windows (both the MinGW and MSVC kits); any recent Qt 6 toolchain with CMake support should work.

```bash
cmake -S . -B build -DCMAKE_PREFIX_PATH="<path to your Qt6 installation>"
cmake --build build
```

The client expects the backend to be running and reachable at `http://127.0.0.1:8000/api/` (see `networkmanager.h`) — start the backend first, then launch the built `bookstore` executable.
